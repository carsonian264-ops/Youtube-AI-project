# Database

PostgreSQL, managed through Prisma (`backend/prisma/schema.prisma`). No table is ever created by hand — every schema change is a Prisma migration (`backend/prisma/migrations/`), applied with `npm run prisma:migrate` (dev) or `npm run prisma:deploy` (production, non-interactive).

## Tables

| Table | Purpose |
|---|---|
| `users` | Accounts. Passwords stored as bcrypt hashes only. |
| `projects` | One row per video project. Owns `status` (the pipeline state machine) and `aspectRatio`. |
| `project_versions` | Reserved snapshot table for full project state at a point in time (forward-compatible with a "restore this version" feature). |
| `scripts` | Versioned structured script/plan JSON (`ProjectPlan` shape). Only one `isActive` row per project. |
| `scenes` | One row per scene: narration, visual prompt, camera direction, duration, sound effect tags, transition. |
| `characters` | The Character/Visual Bible: recurring subjects with appearance, style, palette, environment. |
| `assets` | Every generated file (image/video/audio/music/sfx/thumbnail/final video) with its storage key, provider, and status. |
| `asset_versions` | History of an asset across regenerations. |
| `jobs` | One row per background job: type, status, progress, retry count, error, timestamps. The durable source of truth the frontend polls. |
| `job_attempts` | One row per execution attempt of a job (supports retry/backoff visibility). |
| `videos` | Rendered final videos (there can be more than one across re-renders). |
| `thumbnails` | Generated thumbnails; `isSelected` marks the one used for publishing. |
| `captions` | Generated SRT/VTT caption files. |
| `youtube_accounts` | Connected YouTube channels. OAuth tokens are stored **encrypted at rest** (AES-256-GCM, see `backend/src/utils/crypto.ts`), never in plaintext. |
| `publishing_jobs` | One row per publish attempt: target channel, metadata, visibility, `confirmedByUser`, status, resulting YouTube video id. |
| `usage_records` | Metered usage events (Claude tokens, generations, render seconds, uploads) — the foundation for future billing. |
| `system_logs` | Reserved table for persisted system-level log entries (structured logging currently goes to stdout via Pino; this table exists for future log persistence/audit needs). |

## Key relationships

- `projects.userId -> users.id` (cascade delete)
- `scenes.projectId`, `characters.projectId`, `assets.projectId`, `jobs.projectId`, etc. all cascade delete with their project
- `assets.sceneId -> scenes.id` (nullable — some assets, like the final video or thumbnail, aren't scene-scoped)
- `publishing_jobs.youtubeAccountId -> youtube_accounts.id`
- `job_attempts.jobId -> jobs.id` (cascade delete)

## Indexes

Every foreign key column is indexed (`projectId`, `sceneId`, `userId`, etc.), plus `projects.status`, `jobs.type`, `jobs.status`, and `usage_records.type` for the query patterns the API and workers actually run (list projects by status, poll jobs by project, summarize usage by type).

## Enums

`ProjectStatus`, `AspectRatio`, `JobType`, `JobStatus`, `AssetType`, `AssetStatus`, `PublishVisibility`, `PublishingStatus`, `UsageType`, `CaptionFormat` are all native Postgres enums generated by Prisma — invalid values are rejected at the database level, not just in application code.

## Running migrations

```bash
# create db + apply migrations, local dev
cd backend
npx prisma migrate dev

# production: apply already-created migrations, non-interactively
npx prisma migrate deploy
```

See DEPLOYMENT.md for how this fits into the deploy process, and TESTING.md for how the test database is set up.
